목표

ZYBO Z7-20 보드에서 lwIP RAW API 기반의 TCP Echo Server를 동작시킨다. 클라이언트(PC)가 TCP로 데이터를 전송하면 보드가 그대로 돌려보내는 Callback 구조를 완성하는 것이 최종 목적이다.

🔧
2. 시스템 구성 및 주요 파일

SDT 빌드 플로우란?

Vitis 2024.2부터 도입된 새로운 BSP 생성 방식이다. 기존 xparameters.h 기반이 아닌 Device Tree(DTS)에서 하드웨어 정보를 읽어 CMake 기반으로 BSP를 생성한다. 컴파일 시 -DSDT 플래그가 추가된다.


⚠️ SDT 모드에서는 #ifndef SDT로 감싸진 기존 코드가 전부 비활성화된다. 이것이 이번 작업에서 발생한 대부분의 문제의 근본 원인이다.

원인 분석

오토네고 완료 후 RTL8211E reg17 (PHY Specific Status Register) bit10을 읽어 속도를 판단하는데, 이 레지스터가 계속 0x0000을 반환했다.

원인은 두 가지가 복합적으로 작용했다:

  • IEEE reg1 bit5 래치-하이 동작: FSBL(부트로더)이 PHY 오토네고를 수행한 후 이미 bit5(Autoneg Complete)가 set된 상태로 남는다. 이후 소프트웨어 리셋을 해도 이 래치값이 남아있어, 코드가 오토네고를 기다리지 않고 즉시 통과한다.
  • reg17 타이밍 문제: 오토네고 완료 직후 즉시 reg17을 읽으면 값이 아직 업데이트되지 않아 0x0000이 반환된다.
1차 수정 시도

get_Realtek_phy_speed()에서 오토네고 완료 후 sleep(1) 추가. 그러나 여전히 reg17 = 0x0000.

2차 수정 (래치 클리어) 
/* reg1 첫 읽기로 래치 클리어, 값 버림 */
XEmacPs_PhyRead(xemacpsp, phy_addr, IEEE_STATUS_REG_OFFSET, &status);
status = 0;  /* 강제로 0으로 초기화 */
sleep(1);    /* 실제 오토네고 대기 */

/* 이제 진짜 오토네고 완료를 기다림 */
while ( !(status & IEEE_STAT_AUTONEGOTIATE_COMPLETE) ) {
    sleep(1);
    timeout_counter++;
    if (timeout_counter == 10) { return XST_FAILURE; }
    XEmacPs_PhyRead(..., IEEE_STATUS_REG_OFFSET, &status);
}

결과: PHY_ID1=0x001C (RTL 확인), MDIO 통신 동작 확인. 그러나 여전히 reg17 = 0x0000.

근본 원인

RTL8211E-VL의 reg17(벤더 전용 PHY Specific Status Register)은 ZYBO Z7-20 환경에서 신뢰할 수 없다. 이 레지스터는 PHY 칩 내부 타이밍에 의존적이며, RGMII-ID 모드와 Zynq GEM 조합에서는 값이 업데이트되지 않는 경우가 있다.

해결 방법 — IEEE 표준 레지스터 사용

벤더 전용 reg17 대신 IEEE 802.3 표준 오토네고 결과 레지스터를 사용해 속도를 판단한다.

레지스터이름확인 비트의미
reg10 (0x0A)1000BASE-T LP Statusbit[11:10] (0x0C00)상대방 1Gbps 지원
reg5 (0x05)LP Base Abilitybit[8:7] (0x0180)상대방 100Mbps 지원
reg5 (0x05)LP Base Abilitybit[6:5] (0x0060)상대방 10Mbps 지원
/* reg17 대신 IEEE 표준 레지스터로 속도 결정 */
u16_t lp_1000, lp_100_10;
XEmacPs_PhyRead(xemacpsp, phy_addr,
        IEEE_PARTNER_ABILITIES_3_REG_OFFSET, &lp_1000);   /* reg10 */
XEmacPs_PhyRead(xemacpsp, phy_addr,
        IEEE_PARTNER_ABILITIES_1_REG_OFFSET, &lp_100_10); /* reg5  */

if      (lp_1000 & 0x0C00)  return 1000;
else if (lp_100_10 & 0x0180) return 100;
else if (lp_100_10 & 0x0060) return 10;
return XST_FAILURE;

원인 분석 — 3단계

① main.c — platform_enable_interrupts() 미호출 (SDT 제외)

/* main.c */
#ifndef SDT
    platform_enable_interrupts();  /* SDT 모드에서는 이 코드가 컴파일 제외 */
#endif

비-SDT 모드에서는 이 함수가 Xil_ExceptionEnableMask(XIL_EXCEPTION_IRQ)를 호출해 CPU IRQ를 활성화한다. SDT 모드에서는 이 호출 자체가 없다.


② platform.c — XTimer_SetInterval / XTimer_SetHandler 호출

/* platform.c (수정 전) */
void init_timer() {
    XTimer_SetInterval(50);                                      /* No-op! */
    XTimer_SetHandler(TimerCounterHandler, 0, XINTERRUPT_DEFAULT_PRIORITY);  /* No-op! */
}

이 함수들이 내부에서 InstancePtr->XTimer_TickInterval 포인터를 호출하는데, 그 포인터가 NULL이다.


③ xtimer_config.h — tick timer 완전 비활성화 (핵심 원인)

/* bsp/include/xtimer_config.h — BSP 자동 생성 파일 */
/* #undef XTICKTIMER_IS_SCUTIMER */  ← scutimer tick 비활성화
#define XTIMER_NO_TICK_TIMER   1     ← tick timer 없음으로 명시

BSP가 XILTIMER_tick_timer = None으로 생성되어 XTICKTIMER_IS_SCUTIMER가 정의되지 않는다. 이로 인해 scutimer.c의 #ifdef XTICKTIMER_IS_SCUTIMER 블록 전체가 컴파일에서 제외된다. 결과적으로 XTimer_SetInterval()과 XTimer_SetHandler()는 함수 호출 시 아무것도 하지 않는다.

🔴 타이머 인터럽트가 전혀 설정되지 않아 dhcp_timoutcntr이 절대 감소하지 않고, DHCP 대기 루프가 무한 반복된다.
해결 — xiltimer 우회, SCU 타이머 직접 설정

xiltimer API를 완전히 우회하고 XScuTimer_* 드라이버를 직접 사용하도록 platform.c를 수정했다.

/* platform.c (수정 후) — #ifdef SDT 블록 */
#include "xscutimer.h"

static XScuTimer ScuTimerInst;

static void ScuTimerIntrHandler(void *CallBackRef)
{
    (void)CallBackRef;
    XScuTimer_ClearInterruptStatus(&ScuTimerInst);  /* 인터럽트 클리어 필수 */
    timer_callback();
}

void init_timer()
{
    XScuTimer_Config *ConfigPtr;

    /* SCU 타이머 초기화 (SDT: DeviceId 대신 BaseAddr 사용) */
    ConfigPtr = XScuTimer_LookupConfig(XPAR_SCUTIMER_BASEADDR);
    XScuTimer_CfgInitialize(&ScuTimerInst, ConfigPtr, ConfigPtr->BaseAddr);
    XScuTimer_EnableAutoReload(&ScuTimerInst);

    /* 50ms 주기: SCU 타이머 = CPU_CLK/2, 50ms = (CPU_CLK/2) / 20 */
    /* XPAR_CPU_CORE_CLOCK_FREQ_HZ = 666,666,687 → / 40 = 16,666,667 ticks */
    XScuTimer_LoadTimer(&ScuTimerInst, XPAR_CPU_CORE_CLOCK_FREQ_HZ / 40);
    XScuTimer_EnableInterrupt(&ScuTimerInst);
    XScuTimer_Start(&ScuTimerInst);

    /* GIC 등록 + CPU IRQ 활성화 (Xil_ExceptionEnable() 내부 호출) */
    XSetupInterruptSystem(&ScuTimerInst,
                          (Xil_InterruptHandler)ScuTimerIntrHandler,
                          ScuTimerInst.Config.IntrId,
                          ScuTimerInst.Config.IntrParent,
                          XINTERRUPT_DEFAULT_PRIORITY);
}
✅ XSetupInterruptSystem 내부에서 XEnableIntrId() + Xil_ExceptionEnable() 자동 호출 → GIC 인터럽트 활성화 + ARM CPU IRQ 활성화 완료

7. 핵심 개념 정리
🔌
SDT 빌드 플로우
Vitis 2024.2 신규 방식. -DSDT 플래그로 기존 코드 대부분이 #ifndef SDT로 제외됨. BSP는 Device Tree 기반으로 자동 생성되며 직접 수정 시 재빌드 시 덮어써질 수 있다.
⚡
IEEE reg1 래치-하이 동작
bit5(Autoneg Complete)는 래치-하이 비트. FSBL이 남긴 값이 남아 소프트웨어 리셋 후에도 완료된 것처럼 보임. 반드시 한 번 읽어서 클리어한 후 다시 폴링해야 한다.
📡
RTL8211E reg17 비신뢰성
ZYBO Z7-20 + Zynq GEM + RGMII-ID 조합에서 RTL8211E의 벤더 전용 reg17이 0을 반환하는 문제. IEEE 표준 레지스터(reg5/reg10)로 대체하면 안정적으로 속도 판단 가능.
⏱️
SCU 타이머 직접 제어
xiltimer의 tick_timer가 None으로 설정된 경우 XTimer_SetInterval/SetHandler는 No-op. XScuTimer_* 드라이버를 직접 사용해 50ms 인터럽트를 설정해야 한다. SCU 타이머 클록 = CPU_CLK/2.
🔗
XSetupInterruptSystem
SDT 모드의 인터럽트 설정 통합 API. GIC 핸들러 연결 + GIC에서 해당 인터럽트 활성화 + Xil_ExceptionEnable()로 CPU IRQ 활성화까지 한 번에 처리한다.
🌐
lwIP RAW API Echo 구조
recv_callback()에서 수신 pbuf를 tcp_write()로 그대로 전송. 메인 루프에서 xemacif_input()으로 패킷 폴링, TcpFastTmrFlag/TcpSlowTmrFlag로 TCP 타이머 관리.
🚀
8. 다음 단계 (Ethernet Callback 구현)

recv_callback() 수정 포인트

현재 echo.c의 recv_callback()에서 수신 데이터를 그대로 되돌려 보낸다. 여기를 수정하면 원하는 Ethernet 콜백 로직을 구현할 수 있다.

/* echo.c : recv_callback() — 현재 코드 */
err_t recv_callback(void *arg, struct tcp_pcb *tpcb,
                    struct pbuf *p, err_t err)
{
    if (!p) { tcp_close(tpcb); return ERR_OK; }

    tcp_recved(tpcb, p->len);   /* 수신 확인 */

    /* ↓ 이 부분을 원하는 로직으로 교체 */
    if (tcp_sndbuf(tpcb) > p->len)
        err = tcp_write(tpcb, p->payload, p->len, 1);  /* echo */

    pbuf_free(p);
    return ERR_OK;
}
💡 p->payload: 수신 데이터 포인터 / p->len: 데이터 길이. 수신된 데이터를 파싱해서 다른 처리(GPIO 제어, 센서 데이터 전송 등)를 추가할 수 있다.
